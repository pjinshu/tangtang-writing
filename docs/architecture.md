## 这是什么

**糖糖写作**是一款面向长篇网文的 AI 写作智能体。

市面上的 AI 写作工具大多解决"写一章"——单章质量都不差。但长篇的难点从来不在第一章，而在**第四十章之后**：人物开始走形、设定前后打架、伏笔埋了不回收。

糖糖的思路是：**不让模型"自由发挥写一本"，而是把长篇写作拆成一条有闸门的流水线。**

```
构思 → 深化 → 人物 → 分卷 → 分章 → 框架 → 初稿 → 审查 → 定稿
```

每一步都有产出，**上一环的产出强制注入下一环**。缺了上一环，下一环不启动。

## 核心设计

### 一、六层架构，职责分离

| 层 | 职责 |
|---|---|
| **作者** | 提出构思、做判断 |
| **主控·状态机** | 不生成内容，只做决策与调度 |
| **规则卡** | 领域知识层，声明式规则，按环节加载 |
| **大模型** | 无状态执行者，只负责当前这一步 |
| **质量闸门** | 确定性程序，负责校验 |
| **成果落地** | 持久化与台账更新 |

关键在于：**决策、生成、验证三件事被彻底分开。**
决策交给状态机（不交给模型）；生成交给模型（不让它做判断）；验证交给程序（不让模型自评）。

> 这三件事混在一起，是绝大多数 AI 写作工具写不长的根本原因——模型既当运动员又当裁判，它当然觉得自己的产出没问题。

### 二、四本台账，解决"记不住"

把记忆从对话上下文里拿出来，放到程序侧的结构化台账：

- **章节摘要** — 快速掌握前情
- **事实台账** — 沉淀已确立的设定
- **伏笔台账** — 追踪埋设与回收状态
- **人物库** — 锁定身份、关系与能力边界

写到哪一章，就取那一章真正需要的信息注入。模型不需要记住整本书。

### 三、三层嵌套循环

长篇不能被当成"一个任务"——没有系统能一口气生成 70 万字。所以切成三层：

- **逐章循环** — 写完一章，自动开下一章
- **逐卷循环** — 写满一卷，自动做下一卷的分卷分章
- **全书循环** — 一直推到完本，整本交付

每一层都有明确的完成条件，所以进度永远可查、可停、可续。

### 四、五道质量闸门

| 闸门 | 拦什么 |
|---|---|
| 确认门 | 由作者确认才推进 |
| 承接硬门 | 上一章没定稿，下一章框架不生成 |
| 字数门 / 假完成门 | 字数不达标或"显示完成但无内容" |
| 防跳章 / 防跳卷 | 连续编号，缺号即拦 |
| 卷末对账门 | 伏笔、章号自动核对 |

**闸门不是"更严格的检查"，而是"更便宜的返工"**——写到 200 章发现第 30 章的伏笔没回收，你要改的不是第 30 章，是中间 170 章的连锁关系。

### 五、三键分权

作者用三个键区分三种意图：

| 键 | 作用 |
|---|---|
| **确认，继续前进** | 推进流程 |
| **回复或提意见** | 只改当前环节，不往下推 |
| **自由输入** | 跨环节干预（最高权限） |

> 为什么必须拆开？因为只有一个输入框时，系统无法判断你是要"推进"、"修改"还是"改流程"。三方（模型推理、程序流程、作者想法）一旦不一致，系统就会卡死。

## 实测数据

> 以下为开发团队的内部实测记录，**不等同于对使用者的效果承诺**。写作结果与题材、作者参与程度、平台标准相关。

| 指标 | 数据 |
|---|---|
| 最长连续推进 | **260+ 章** |
| 单本字数 | 约 **69 万字** |
| 单次连续产出 | **15 小时**（单驱动） |
| 跨卷自动拉起 | **3 次**（全自动，零人工干预） |
| 全程人工介入 | **2 次**（337 章全程） |
| 文风漂移 | 无（全书一套笔调） |

**一致性核验方式**：章题是否等于分章规划、伏笔是否按期回收、单章字数是否达标、跨卷是否按规划收束 —— 全部由程序逐项判定。

**作品成果**：已签约 **15 本**（长篇 5 + 短故事 10），已完结完整本 1 本，获番茄平台推荐。

## 它做不到什么

我们不想把 README 写成宣传页，所以这几句必须说：

- **文风的华丽程度取决于所用模型。** 工具能做的是"把全书笔调锚住"，不是"把文笔提到人类头部作者的水平"。
- **它要求作者参与。** 每个环节需要你确认，不是"输个题目就出一本书"。
- **剧情能不能抓人，核心还是作者的活。** 它吐出来的东西往往没毛病，但也难出彩。出彩那部分，是人的工作。
